# Course-wide files

These files live in the student's Claude Project and persist across many runs and
many study sessions. The student downloads them, works with them (by hand and via
the tutor), and re-uploads them. That means **you will frequently receive an
existing version that already contains the student's own data.** The cardinal rule:

> **Merge, never clobber.** Read the existing file first. Preserve every row,
> status, date, and note the student (or a past session) entered. Only append new
> material and update cells you have fresh evidence for.

If you cannot find an existing version in the uploads or project, treat it as the
first run for that course and create the file from its template in `assets/`.

---

## topic-tracker.md

One row per **trackable topic**, across **all** digested lectures for the course.
Template: `assets/topic-tracker-template.md`. Columns: Lecture · Topic · Status · Last
reviewed · Notes/open questions. Status is one of `new | weak | ok | strong`.

### Granularity — this is the part that's easy to get wrong

A tracker row is a **review-sized chunk the student would rate as a unit**, not a
glossary entry. The digest already stores every term and definition — the tracker is
the *review index over* the digest, not a second copy of it. So do **not** create one
row per defined term. That produces a 20-row wall for a single lecture that's useless
for studying and planning: the student can't meaningfully rate twenty things, and a
study session targets areas, not individual definitions.

Operational test for whether something deserves its own row: *would the student
plausibly rate their confidence in it separately, and would a study session spend a
real chunk of time on it?* If it's a single definition you'd cover in two minutes, it
belongs *inside* a topic, not as its own row.

Aim for the lecture's **major examinable themes** — typically a small handful (around
**3–6** for a broad lecture, as few as 1–2 for a tightly focused one). When unsure, go
coarser: it's easy for the student (or the tutor) to split a topic later, and painful
to wade through a glossary. Derive the themes from the digest's structure and the
lecturer's own sectioning — group the fine-grained terms under the parent theme they
belong to. Split out a sub-topic only when it's practically distinct enough to study
and rate on its own (e.g. a specific tool/syntax, or a self-contained method).

**Worked example.** A broad first-lecture deck on knowledge representation might have
~20 terms in its digest (entailment vs provability, vocabulary Σ, terms vs wffs,
free/bound variables, interpretations, satisfaction, reification, deduction/induction/
abduction, situation calculus, temporal reasoning, resolution, TPTP/Vampire,
undecidability of FOL, LLMs vs symbolic reasoning, …). That collapses to roughly:

- KR&R foundations & logical entailment (model- vs proof-based, ⊨ vs ⊢)
- First-order logic: syntax, semantics & formalization
- Inference: reasoning modes, resolution & (un)decidability
- Situation & temporal calculus
- Automated theorem proving in practice (TPTP / Vampire)
- LLMs vs symbolic reasoning

— about six rows, not twenty. Fewer is fine too; the student can ask to split any of
these when a topic turns out to be where they're weak.

### On each lecture digest run

1. Read the existing tracker if present.
2. Decide the new lecture's trackable topics using the granularity guidance above.
3. For each, check whether a matching row already exists (match loosely on topic
   name — don't create near-duplicate rows for the same theme under different wording).
4. Append genuinely new topics as new rows with status `new`, last-reviewed `—`, and
   any open question from the digest in the notes column.
5. Leave all existing rows exactly as they are — their status, dates, and notes are the
   student's mastery record. Do not reset them to `new`.

When the tutor updates the tracker at session end, the same discipline applies: update
only the rows for topics actually reviewed, and only the cells with new evidence. If a
session reveals a topic is really two things the student rates differently, splitting a
row then is fine — that's the granularity earning its keep.

## learning-profile.md

Cross-course file — it is meant to outlive this one course and travel to the next.
Template: `assets/learning-profile-template.md`. Sections: "How I learn best",
"Common mistake patterns", "Topics I find hard across courses".

Rule: **create it only if it does not already exist.** If it exists (even from a
different course), leave it untouched during digest runs — it gets filled in
gradually during study sessions, with the student's agreement, not bulk-generated.
Never overwrite an existing profile.

---

## study-plan.md

Generated by a separate flow, not during a plain digest run. See
`references/study-plan.md` for the full generation logic (cold-start vs real
mastery data, full-prep vs sprint mode, self-assessment and diagnostic passes).
Like the others, when regenerating, fold in the current tracker state rather than
discarding the student's progress.

## Where files go

Write the course-wide files and the per-lecture digests to
`/mnt/user-data/outputs/` so the student can download them, then present them. The
course-wide files have fixed names — `topic-tracker.md`, `study-plan.md`,
`learning-profile.md` — so re-uploads line up. Per-lecture digests follow the uniform
convention `digest-<NN>-<slug>.md` (two-digit zero-padded lecture number + a short
kebab-case topic slug, e.g. `digest-03-dynamic-programming.md`). **Before naming a new
digest, check the digests already present and match the established pattern** — see the
*Merge fragments into the final digest* step in `SKILL.md` for the full rule. Uniform,
stable names are what let the tracker, the tutor, and the student refer to lectures
consistently across runs.
